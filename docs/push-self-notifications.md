# Push notifications for your own messages

## Symptom

After sending a message from the app, the device sometimes shows a push
notification for that same message.

## Root cause

Push is generated by the XMPP server, not by the app. `mod_cloud_notify` sends a
XEP-0357 push for every archived message whose destination is the user, but only
to push registrations that have **no active session**. The app's own outgoing
message is archived too. If the app's session is gone or considered dead when
the archive event fires (the app was backgrounded, killed, or the connection was
slow/hibernated), the server pushes the user's own sent message back to the
device. The OS displays that push before any JavaScript can run, so the app
cannot reliably suppress it on the client.

The same archive event also drives legitimate notifications, so the fix is to
filter out only messages whose sender is the push recipient.

## Fix 1 — server-side (required for background pushes)

Install `docs/prosody/mod_cloud_notify_self_filter.lua` as a Prosody module. It
blocks a push when the original stanza's bare `from` is the recipient's own bare
JID. It hooks both `cloud_notify/push` (Prosody 13+ / recent `prosody-modules`)
and `archive-message-added` (older `mod_cloud_notify` versions):

```lua
if jid.bare(from) == jid.join(username, module.host) then
    return true; -- block the push
end
```

Install on the Snikket/Prosody host:

```sh
cp docs/prosody/mod_cloud_notify_self_filter.lua /etc/prosody/modules/
# add "cloud_notify_self_filter" to modules_enabled in prosody.cfg.lua
prosodyctl restart
```

Verify in the Prosody log at debug level: sending a message from the app and
then closing it must not produce a push for that message. Incoming messages
must still notify.

### Limitation

The filter matches the sender's bare JID, so it covers 1:1 messages. A message
you send to a MUC is reflected with `from='room@muc/nick'`, which cannot be
matched to your account from the stanza alone. The app-side foreground
suppression covers that case while the app is open; a background self-MUC push
would need the MUC module/room configuration to suppress it.

## Fix 2 — app-side (foreground only)

`src/utils/push.ts` now clears delivered notifications after a successful send
(`suppressOwnMessageNotifications`) and retries briefly to catch a push that
races the send. The `notificationReceived` listener does the same for any push
received while the app is foregrounded.

This does not help when the app is in the background: the OS shows the
notification before the JS listener runs. Use the server-side module for that
case.

## Related

The existing ghost-notification filter in fpush (`docs/ghost-notifications.md`)
drops pushes for unimportant stanzas (typing, receipts, markers). This document
covers the remaining case: a real message whose sender is the recipient.
